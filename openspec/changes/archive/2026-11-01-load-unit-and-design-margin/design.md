# Design

## Context

动机见 `proposal.md`，行为契约见本次四份 delta spec。本文只记录实现层的取舍。

**当前状态（口径 v1）**

- 负荷在进入计算前乘以 `load_coe = 0.001`（按"数据是 W"处理），设备默认值又被 ÷26.58 缩到 278 kW 一级
- 冷机按 `scale_ratio = Q_r/2112.6` 线性放大功率；水泵、冷却塔通过 `kG/kH/kGw/kGa` 做相似换算
- 这一整套的存在理由，是让 7.4 MW 的默认装机与"看起来只有几百 kW"的负荷匹配

**现状的根因**

建筑空调面积极值被写成 **2,931 m²**，实际为 **2,931,000 m²**。面积差 1000 倍，才使"负荷是 W"成为当时唯一自洽的解释。面积纠正后：峰值 103.4 W/m²、年冷量 51.1 kWh/m²·yr，均落在常规办公建筑区间。

**数据与模型的尺度约束（未变）**

三个 ML 模型都在**单机参考点**附近训练：冷机 2,112.6 kW、水泵设计流量约 182 L/s、冷却塔设计水流量 200 L/s / 风量 58,910 m³/h。因此实际机组容量一旦放大，喂给模型的工况点必须折算回参考尺度。

## Goals / Non-Goals

**Goals**

- 负荷不做任何换算，直接以 kW 参与计算
- 用户能直接看到"装机够不够"（设计裕度）与"实际机组是模型的多少倍"（放大系数）
- 三个设备模型的尺度折算收敛为**一个显式系数**，不再散落在默认值与相似换算里

**Non-Goals**

- 不重训模型、不改变模型权重
- 不做自动选型推荐
- 不改动负荷数据文件内容

## Decisions

### D1 面积默认值与允许上限

**决策**：默认空调面积改为 **2,931,000 m²**；请求模型的面积上限由 1,000,000 放宽到 **10,000,000**（下限仍为正数）。

**理由**：原上限会把该项目的正确面积直接判为非法（422），必须同步放宽；下限保持"正数"以兼容小项目。

**替代方案**：把面积做成无上限。否决理由：完全无上限会让 EUI 等强度指标出现无意义的除零级误差，保留一个宽松上限更安全。

### D2 删除 `load_coe` 采用"直接移除 + 口径版本升级"

**决策**：请求、算法配置、结果元信息中全部移除 `load_coe`；`口径版本` 由 `v1` 升为 `v2`。不做"传了也接受但忽略"的兼容层。

**理由**：该参数唯一作用是错误换算，保留兼容只会让新旧结果混在一起而无法察觉。口径版本升级让"不可与历史结果对比"这件事可被程序读取。

**替代方案**：保留字段但恒为 1.0。否决理由：会出现"看起来能传、实际无效"的僵尸参数，正是本次要清理的对象。

### D3 设计裕度：前端实时展示、后端复算落地

**决策**：前端用解析后的负荷数据最大值与当前选型实时算出裕度并展示；后端在仿真开始时用**服务端收到的数据**复算一次，以服务端结果写入 `meta.designMargin`。

**理由**：前端需要"改台数立刻看到裕度变化"的即时反馈；但结果里记录的必须是服务端实际参与计算的那一份，否则报告与界面可能不一致。

**替代方案**：只用后端计算。否决理由：用户要等到提交后才知道裕度，失去"边调边看"的意义。

### D4 放大系数为主，单机容量派生只读

**决策**：`冷机容量放大系数` 是可编辑参数（默认 20.0）；`大/小机额定制冷量` 改为**只读派生显示** = `2112.6 × 系数`（小机同理需明确其参考容量）。

**理由**：两个入口并存必然打架。以系数为主，是因为模型的参考容量是固定事实（2112.6 kW），而"实际机组多大"正是用户真正要表达的信息。

**替代方案**：以容量为主、系数派生只读。否决理由：那样用户仍需自己知道 2112.6 这个模型常数才能理解系数含义；以系数为主更贴近"这台机器是模型的多少倍"这一心智模型。

**待定**：小机的参考容量。模型只有一套 `model.pth`，参考容量为 2112.6 kW；小机若仍按 1056.3 处理，其放大系数应为 `1056.3/2112.6 × N = 0.5N`。任务中按"大小机共用同一系数、但各自额定容量仍按 1:0.5 比例"实现。

### D5 尺度折算的数学：输入 ÷ N、输出 × N

**决策**：设放大系数为 N，则对三个模型统一执行：

| 设备 | 模型输入 | 模型输出 |
|---|---|---|
| 冷机 | 负荷率、供/回水温度（无量纲与强度量）—— 不折算 | 功率 × N |
| 水泵 | 流量 G ÷ N，扬程 H 不折算 | 功率 × N |
| 冷却塔 | 水流量 ÷ N、风量 ÷ N，温度不折算 | 风机功率 × N |

**理由**：实际机组的流量是参考机组的 N 倍（同 ΔT、同容量比），若直接喂 2,000+ L/s 给训练域在 ~182 L/s 的模型即为外推。折算输入 + 放大输出，等价于"几何相似设备在同一无量纲工况点下，功率按容量比放大"。

**说明**：用户原话只提到"缩放模型输出"。输入侧若不同步折算，模型会长期工作在训练域外，结果不可信，因此这里补上了输入折算——这是对需求的必要补全，已在 proposal 中说明。

**替代方案**：只缩放输出。否决理由：模型外推，且与 D5 上一版（相似换算）相比并没有更简洁。

### D6 数据文件位置：集中到一个常量

**决策**：数据目录按现状保留在 `src/main/buildingload/`；在 `buildingload.py` 与自检脚本中各引入一个解析函数/常量指向该目录，不再散落相对路径。

**理由**：用户已明确不移动文件。集中一处后，将来若要迁移只改一个常量。

**风险记录**：算法层依赖前端目录属于临时安排，已在 Risks 中登记。

## Risks / Trade-offs

- [口径变更导致历史结果不可比] 面积差 1000 倍、删除换算后，EUI/碳排强度等指标量级全变 → 缓解：口径版本 v2 写入 meta，报告与界面标注"旧结果不可直接对比"。
- [模型外推] 放大系数过大或过小都会让模型偏离参考点 → 缓解：结果记录系数；界面在系数明显偏离默认值时提示；报告披露。
- [输入/输出折算不对称] 若某处漏乘或漏除 N，结果会差 N 倍且不易察觉 → 缓解：以"分项加和守恒"与"设计裕度"两条不变量做回归核对。
- [台数上限 10 与容量组合] 默认系数 20 时 7~8 台即可达标；但若用户把系数调小，10 台上限可能不足以达到 0.9 → 缓解：裕度提示会直接显示"偏小"，不静默。
- [面积上限放宽] 超大面积会让 EUI 趋近 0 → 缓解：上限仍有界（1,000 万 m²），且报告展示的是绝对量。
- [数据位于 src/main] 算法依赖前端目录 → 缓解：集中常量；登记为待迁移项。

## Migration Plan

1. **口径与常量**：面积默认值/上限、口径版本 v2、数据目录常量
2. **算法层**：移除 `load_coe` 与旧缩放，引入统一的放大系数（输入折算 + 输出放大）
3. **后端**：schema 增删、meta 新增三项、设计裕度计算
4. **前端**：删除量纲换算系数、新增放大系数与只读裕度、面积默认值
5. **报告**：第 3 章展示两项新指标
6. **回归**：以默认系数 20、大机 7 台验证裕度 ≈ 0.976；分项加和守恒；全年结果量级与 51.1 kWh/m²·yr 的冷量强度一致

**回滚**：纯代码回滚，无数据迁移；但旧报告与新报告口径不同，回滚后历史报告仍保留 v2 标记。

## Open Questions

- **默认台数是否直接改为 7**：这样默认场景下裕度即为 0.976，用户打开界面就看到合格值。属产品默认值选择，不影响契约，可在实施时决定。
