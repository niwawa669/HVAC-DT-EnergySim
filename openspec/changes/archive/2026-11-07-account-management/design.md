# Design

## Context

账户数据已存在：`users` 表（id、username、email、hashed_password、role、is_active、created_at、updated_at），登录用 bcrypt 校验并签发 JWT；`api/deps.py` 每次请求按令牌里的 `uid` 从数据库读取账户，并根据库中的 `role` 与 `is_active` 做鉴权。也就是说"账户状态即时生效"的基础已经具备，缺的只是管理接口与界面。

本次实现已经完成并通过验证（`scripts/verify_accounts.py` 24 项断言、`vue-tsc` 零错误、真实 HTTP 联调），本设计记录当时的取舍，避免后续重复讨论。

## Goals / Non-Goals

**Goals:**

- 普通用户能自助修改邮箱与密码，且改密必须校验当前密码。
- 管理员能分页/检索账户，并完成新建、改属性、重置密码、删除。
- 权限边界由服务端强制：非管理员 403；不能操作自己到失去登录能力；不能移除最后一个管理员；不能删除有历史数据的账户。
- 停用与角色变更在下一次请求生效，无需重启或重新登录。
- 前端入口清晰：个人设置常驻，用户管理仅管理员可见且不可绕路由访问。

**Non-Goals:**

- 不引入 SSO / LDAP / OAuth、邮箱验证、邮件找回密码、MFA。
- 不做细粒度资源权限（项目级成员、按项目授权）；角色仍只有 admin / engineer。
- 不做操作审计日志与登录历史。
- 不改变密码哈希算法，不引入令牌版本号/主动吊销机制。
- 不新增数据库表或迁移。

## Decisions

### D1 复用 users 表，不新增角色/权限表

**选择**：角色仍是 `users.role` 的单值字符串（`admin` / `engineer`），启用状态用 `users.is_active`。

**理由**：系统只有两类角色，权限判断集中在"是否管理员"；引入角色表与关联表会带来迁移与联表成本，却没有实际收益。若未来出现多角色/细粒度权限，再单独立项。

**备选**：独立 roles / user_roles 表（放弃：当前过度设计）；布尔 `is_admin`（放弃：无法扩展到更多角色）。

### D2 鉴权每次读库，角色/停用即时生效

**选择**：沿用 `deps.get_current_user` 的行为——先按 `uid` 查库，再回退用户名；用户不存在或 `is_active=False` 一律 401；角色取库中值。

**理由**：JWT 里的 `role` 会过期，若信任令牌，管理员降权或停用后旧令牌仍可操作。读库的代价是一次主键查询，完全可以接受。

**代价**：每请求多一次查询；**缓解**：主键查询，SQLite 本地开销可忽略。

### D3 保护规则放在服务端，前端只做提示

**选择**：以下规则在路由层强制，前端禁用按钮仅改善体验：

- 非管理员访问 `/api/users` → 403
- 修改自己：角色不得变、`isActive` 不得为 false
- 目标为启用管理员且变更会移除其管理员身份/启用状态时，检查"除目标外仍有启用管理员"
- 删除自己 → 400
- 删除启用管理员且其为最后一个 → 409
- 删除有项目或仿真任务的账户 → 409，提示改为停用

**理由**：前端可以被绕过（直接调用接口），权限必须在服务端判定；把规则集中在一个路由文件也便于审计。

**代价**：并发管理员同时降权同一批账户时，"最后一个管理员"检查存在理论上的检查-写入竞态。**缓解**：单站点、管理员数量极少；SQLite 串行写事务下实际风险很低。若未来多管理员高并发操作，再加数据库约束或行锁。

### D4 删除与停用分开

**选择**：删除只允许"无项目、无仿真任务"的账户；有历史数据的账户必须停用。

**理由**：`projects.owner_id`、`simulation_tasks.user_id` 都是外键，直接删除会破坏归属（或需要级联删除历史数据）。停用保留数据归属，同时阻断登录，是更安全的默认动作。

**备选**：软删除字段 `deleted_at`（放弃：与 `is_active` 语义重叠，且需全局过滤）；级联删除（放弃：会丢历史结果与报告归属）。

### D5 密码策略与重置

**选择**：bcrypt（沿用 `passlib`）；长度 6–72；自助改密必须校验当前密码，且新密码不得与当前密码相同；管理员重置无需旧密码。接口不返回任何密码字段。

**理由**：与既有登录实现一致，不引入新依赖；6 位是当前演示系统的最低门槛，72 是 bcrypt 的输入上限。管理员重置是必要的运维路径（用户忘记密码时）。

**代价**：无强度检测、无历史密码复用限制。**缓解**：在文档中写明当前策略；需要更强策略时单独立项。

### D6 接口形状与状态码

**选择**：请求/响应字段用 camelCase（`isActive`、`newPassword`、`currentPassword`），与既有项目/仿真接口一致；语义状态码：

| 情形 | 状态码 |
|---|---|
| 非管理员 | 403 |
| 用户名重复 | 409 |
| 最后一个管理员 / 有关联数据 / 操作自己 | 400 或 409（按语义） |
| 账户不存在 | 404 |
| 当前密码错误、新旧密码相同 | 400 |
| 用户名/密码格式不合规 | 422（Pydantic 校验） |

**理由**：前端拦截器按状态码统一提示；422 由 FastAPI 自动生成，避免重复校验。

### D7 前端结构

**选择**：

- `/account`（所有登录用户）：资料卡 + 改密卡；保存资料后同步 `userStore`。
- `/admin/users`（仅管理员）：搜索、分页、新建/编辑/重置/删除对话框；编辑自己时角色与启用开关禁用。
- 路由 `meta.requiresAdmin` + 全局守卫：非管理员访问直接回首页。
- `AppLayout` 顶栏改为用户下拉菜单（账户设置 / 退出登录）；进入布局时调用一次 `/auth/me`，同步角色与邮箱，避免管理员改角色后菜单不更新。

**理由**：入口符合常见后台习惯；角色同步解决"本地 store 与数据库不一致"的问题，同时让停用账户在进入页面时被 401 拦截。

## Risks / Trade-offs

- **[风险] 改密后已签发令牌仍有效** → JWT 无状态，本次未引入令牌版本号；密码修改能阻止"新登录"，不能立即踢掉已登录会话。**缓解**：令牌有效期 7 天；若需要强制下线，后续增加 `token_version` 字段并在鉴权时比对。
- **[风险] 邮箱只做长度限制，不做格式校验** → 当前邮箱仅用于展示/联系，不参与登录；**缓解**：需要邮件通知时再引入 `EmailStr` 与验证流程。
- **[风险] 无审计日志，管理员操作不可追溯** → 单站点小团队可接受；**缓解**：后续可在仓储层加操作日志表，不影响本次接口形状。
- **[风险] 并发管理员同时降权导致零管理员** → 检查与写入非原子；**缓解**：单写库 + 极少并发；若上多实例，用数据库约束或串行化事务兜底。
- **[风险] 删除账户后其历史报告 `ownerId` 悬空** → 报告索引不设外键，下载仍可用，归属校验退化为"管理员可见"；有项目/任务的账户本就禁止删除，实际影响很小。

## Migration Plan

1. 无需数据库迁移：`users` 表结构不变，默认账户与密码保持原样。
2. 部署：后端新增路由（重启生效），前端新增两个页面与路由（刷新/热更新生效）。
3. 回滚：回退代码即可；已创建的账户与修改记录留在库中，不影响旧版本登录与鉴权。
4. 验证：`python scripts/verify_accounts.py`；`python scripts/verify_persistence.py` 回归；`vue-tsc --noEmit`。
