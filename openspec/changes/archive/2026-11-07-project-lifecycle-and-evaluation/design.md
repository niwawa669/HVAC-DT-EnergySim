# Design

## Context

本 change 的实现先于本文档落地：`ProjectNew.vue`、`algorithm_wrapper.py`、`radarMetrics.ts` 的最后修改时间早于 delta spec 的写入时间。因此本文记录的是"已被实现选定的做法为何成立、边界在哪"，而不是实现前的规划。动机见 `proposal.md - Why`。

四条既有约束决定了下文的取舍：

- **参数真相在后端**：`persistence-framework` 的 D2 规定结果参数快照一律按后端实际生效值生成，不采用调用方提交的 `parameters`。因此参数本来就有两份、且会分叉：`task.config`（提交原值）与 `result.meta.parameters`（生效值，含派生与修正）。
- **`projectId` 可空**：`persistence-framework` 的 D14 规定任务可以没有项目关联，此时结果里 `projectId` 返回 0，前端不校验非零。
- **迁移按版本只跑一次**：`app/db/migrate.py` 以 `schema_migrations` 为水位线，已记录的版本不再执行。
- **`Project.config` 列存在但从未写入**：`ProjectCreate` 不接收它，`get_or_create_for_simulation` 不传它，这块地是空的。

一个现状故障把上面几条串了起来：删除项目会把其任务置为未关联，而启动流程每次都会为"没有 project_id 的任务"回填项目（`main.py` 调用 `backfill_task_links`）。于是 `project_id IS NULL` 同时表示"改动前的遗留任务"与"用户主动删除后的解绑"，回填无法区分，删除在下次启动时失效。

## Goals / Non-Goals

**Goals:**

- 使"删除项目"在服务重启后依然成立，且不引入软删除
- 让 `project_id IS NULL` 恢复单一语义
- 把"项目是什么、不做什么"固定下来，避免 README 与界面继续暗示它持有方案
- 明确"评价分数在视图侧计算"这一选择的代价边界

**Non-Goals:**

- 项目不持有参数，不支持回放与方案容器（`Project.config` 保持空置）
- 不引入任何删除痕迹字段（`deleted_at` / `unlinked_at` / 已删除状态位）
- 不提供孤儿结果（删项目后解绑的任务）的界面入口
- 不调整雷达图基准数值与"冷源站占建筑总量 35%"的折算假设
- 不做任务、结果、报告的留存与清理策略（沿用 `persistence-framework` 的 Open Question）

## Decisions

### D1 删除是硬删除，不引入墓碑字段

**选择**：删除项目时 `DELETE` 项目行，并把其任务 `project_id` 置空；不新增 `deleted_at`、`unlinked_at` 或任何"已删除"状态。

**理由**：项目行只是结果的分组标签，任务、结果、报告都按 `task_id` 独立存储，删掉分组不影响任何数据。墓碑字段会把"删除"变成一个所有读取路径都必须记得过滤的状态——列表、详情、统计、报告、回填，漏一处就复活，而收益只是留一条审计痕迹。

**代价**：删除不留可追溯记录（谁在何时删了哪个项目）。**接受**：若日后需要审计，应作为独立 change 增加操作日志，而不是在项目表上挂状态位。

**替代方案**：软删除（否决，与"从数据库完全删除"的口径冲突）；级联删除任务与结果（否决，spec 要求保留仿真历史）。

### D2 历史回填降级为一次性数据迁移（v2），撤出启动流程

**选择**：新增 migration v2，在结构升级时按（用户, 项目名）为当时 `project_id IS NULL` 的任务建/复用项目并回填；`main.py` 启动序列不再调用回填。

**理由**：回填的原始意图是"给改动前提交的老任务补数据"，这是一次性数据迁移，不是常驻业务逻辑。放在启动流程里，它就成了无限期规则，把删除产生的 `NULL` 重新解释成"待回填"。迁移器本来就按版本只跑一次，`schema_migrations` 是天然水位线。

**代价**：迁移执行时会把手头所有孤儿任务最后复活一次。**缓解**：迁移打印回填任务数与新建项目数，发布说明写明这是一次性的。

**替代方案**：任务侧加 `unlinked_at` 标记、回填跳过非空行（否决，见 Non-Goals；且要求每条回填路径都记得看标记，漏看即复活）。

**约束**：迁移内用原生 SQL 表达"按 (user_id, project_name) 分组建/复用项目"，不 import 会继续演进的业务函数，否则日后重构会让历史迁移失效。

### D3 删除拒绝条件改为"存在待运行或运行中任务"

**选择**：删除前查询该项目下是否存在 `pending` / `running` 任务（全量，不只最近一条），存在则返回 409。

**理由**：spec 要求如此；现有实现取 `latest_task`（按 `updated_at` 取一条），当运行中的任务不是最新那条时会漏判，把运行中的任务直接解绑。

**代价**：多一次查询，可接受。

### D4 项目不持有参数（文件夹语义）

**选择**：`Project.config` 继续空置；参数真相保持在 `task.config`（提交原值）与 `result.meta.parameters`（生效值）；回放与方案容器记为后续方向。

**理由**：参数已经有两份且会分叉（见 Context 的 D2 约束），再加一份项目级草稿会让"界面填的、算出来的、报告写的"变成三向对账；而回放必须先裁决"回放原值还是生效值"，那本身是一个独立设计。塞进本 change 会让设计文档变成四块互不相关的决策。

**代价**：用户改一个参数要重填表单；同名项目的 `building_type` / `area` 会被后续任务覆盖（`get_or_create_for_simulation`）。**缓解**：文案上把项目表述为"按名称归组的仿真"，不暗示它是方案——README 与列表页措辞需同步。

**替代方案**：轻量回放（推迟，需先裁决参数真相）；方案容器（推迟，需定三份参数优先级并把方案态与任务态分离，规模够独立 change）。

### D5 评价分数在视图侧计算，结果只存原始值

**选择**：结果 JSON 只存原始指标（含 `avgChillerLoadRate`）；0–100 分、等级与 60 分参考线由前端按 `utils/radarMetrics.ts` 的阈值表折算；阈值与折算假设的书面版本在 `docs/radar-benchmark.md`。

**理由**：评价基准会随标准更新。把分数落进结果，等于让每条历史结果携带一份过时基准，还要为每条结果记录基准版本。

**代价**：阈值一改，同一份历史结果的分数与等级随之变化。`result-evaluation` 的"基准更新时不得修改历史结果本身"按字面成立（结果 JSON 未变），但可比较性会漂移。**缓解**：阈值表与折算假设钉在 `docs/radar-benchmark.md`，界面注明"按当前基准折算"。

**替代方案**：分数落进结果 JSON（否决，需给每条结果记录基准版本，且旧结果无分数会变成缺失，兼容成本更高）。

**已知偏差**：旧结果缺 `avgChillerLoadRate` 时，实现仍以 0 分绘制点位，与 `simulation-result` 的"不得按 0 分正常参与评价"冲突；按缺陷处理，见 `tasks.md`。

## Risks / Trade-offs

- **[v2 迁移会复活现存孤儿任务一次]** → 迁移日志打印数量，发布说明写明一次性；如需清理须显式执行数据删除，不在迁移内自动完成。
- **[回滚到旧代码会重新启用每次启动回填]** → 回退后旧代码会把删除过的项目再次复活。数据层可逆（v2 记录仍在 `schema_migrations`，新代码不会重跑），行为层不可逆；回滚说明必须写明这一点。
- **[删除无审计痕迹]** → 接受；审计需求另立 change。
- **[删除后结果在界面不可达]** → 非目标：`GET /api/simulate/list` 仍可查到，接口层不丢数据。
- **[历史分数随基准漂移]** → 阈值表文档化并注明适用范围，不承诺"历史分数稳定"。
- **[迁移与业务代码耦合]** → 迁移只用原生 SQL，依赖表结构而非 repository 函数。
- **[同名项目属性被覆盖]** → 通过文案调整降低误读，不改变数据模型。

## Migration Plan

1. **上线**：部署新代码 → 首次启动自动执行 v2。`DB_AUTO_MIGRATE=false` 时先 `python -m app.db.migrate status` 看待执行，再执行 `upgrade`。
2. **数据**：v2 只写 `projects` 与 `simulation_tasks.project_id`；不改表结构，不动 `data/datasets`、`data/reports` 与结果 JSON。
3. **回滚**：停服 → 回退代码 → v2 记录留在 `schema_migrations`，新代码不会重跑；旧代码会恢复"每次启动回填"，删除过的项目会重新出现（见 Risks）。
4. **校验**：`scripts/verify_persistence.py` 补两条断言（迁移版本为 `[1, 2]`、删除 → 重启后项目不复活）并要求全绿；手工验证旧结果在监控页显示"—（旧结果）"。
