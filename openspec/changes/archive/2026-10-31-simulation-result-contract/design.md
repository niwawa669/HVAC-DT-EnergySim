# Design

## Context

动机见 `proposal.md`，行为契约见本次 change 的三份 delta spec（`simulation-result`、`data-ingestion`、`equipment-config`）。本文只记录实现层的约束与取舍。

当前实现的约束条件：

- **算法层是科研代码**：`station` / `channel` 是纯物理单点模型，`__call__` 输入为「冷负荷、干球温度、含湿量」，不接收也不返回任何时间信息。
- **聚合发生在服务层**：`algorithm_wrapper` 负责按 168 小时切分、逐小时调用、累加。这是唯一知道"第几小时"的地方，也是时间戳与分项丢失的地点。
- **三个设备模型内嵌额定值**：`Chiller.Q_r=2112.6`、`Pump.Gr=182.46/Hr=19.65`、`Tower.Gw_r=200/Ga_r=58910`。`Channel` 通过 `ChannelInfo` 传入的选型参数与这些内嵌值并存，形成双重口径。
- **单通道假设是"一机一泵一塔"**：`channel.thermal_calculation` 先算单台，再乘 `n_active`（冷机台数）。
- **无持久化**：任务与结果驻留进程内存，重启即失。

## Goals / Non-Goals

**Goals**

- 时间、分项、月度、运行统计四类信息从"逐时单点"贯通到"年聚合"，且中途不再丢失
- 结果数值在口径变更后仍可自证：总小时数、分项加和、供冷缺口三处可外部复核
- 选型参数与算法消费范围完全对齐，形成可回显的参数快照

**Non-Goals**

- 不重构为任务队列/多进程（并发与阻塞问题记录为已知风险，本期不处理）
- 不重训或替换任何 `.pth` 模型
- 不引入数据库、不改变接口路径与鉴权
- 不实现设备校准（`coe` 系列旋钮本期移除，校准能力留待二期）

## Decisions

### D1 时间戳全程携带，而非在结果侧反推

**决策**：时间戳从上传数据一路携带到结果，聚合按真实日期分组。

**理由**：现有实现用 `index // 168` 推算周序号。一旦数据非整年、跨年、或存在缺失小时，反推即失真；而"缺小时"恰恰是 `data-ingestion` 明确允许并会报告的情况。

**替代方案**：后端按「数据起始日期 + 行号偏移」推算日期。否决理由：在存在缺失小时的场景下会系统性错位，且错误静默。

### D2 周与月是两个独立的逐时聚合视图，不做层级嵌套

**决策**：周聚合按日历周（周一 00:00 至周日 23:00），首尾可为不满周；月聚合按自然月。二者都直接由逐时序列聚合，互不派生。

**理由**：报告需要"按周看趋势、按月看对比"，两个视图服务不同叙述。若让周嵌套进月，首尾不满周会让月度合计出现出入，反而制造核对困难。

**替代方案**：固定 168 小时连续切段（现状）。否决理由：段边界与日历不对齐，报告无法标注真实起止时间。

### D3 聚合与统计放在服务层，物理模型保持纯函数

**决策**：分项累加、月度聚合、负荷率分布、投运时长统计全部在 `algorithm_wrapper`（及其后继服务）完成；`station` / `channel` 只增加必要字段，不承担聚合职责。

**理由**：单点物理模型不应持有跨小时状态，否则并发与可测试性都会恶化。

**替代方案**：在 `station` 内累计。否决理由：污染纯函数，且与已存在的全局单例问题叠加会放大串扰风险。

### D4 结果采用"固定七区块 + 保留既有字段名"

**决策**：结果新增 `meta`、`monthly`、`breakdown`、`operating_stats`、`peak_context` 五个区块，同时保留 `summary` 与 `weekly` 的既有字段名（语义按 spec 修正）。

**理由**：保留字段名可以把前端改动收敛到"新增消费点 + 修正错误计算"，避免整页重写；七区块确保报告侧无需存在性分支。

**替代方案**：全新结果模型、旧字段全删。否决理由：破坏了 `proposal.md` 里"收益/改动比"的平衡——本 change 的目标是让数字可信，不是重做契约。

### D5 设备额定值由通道配置注入，并施加线性额定缩放

**决策**：`Chiller` / `Pump` / `Tower` 的构造参数接受额定值；当注入额定值与模型参考额定值不一致时，对模型输出的**功率**按额定容量比例线性缩放，并在结果 `meta` 中记录缩放已生效。

**理由**：ML 模型的输入是负荷率、温度等无量纲/工况量，输出是"参考机组在该工况下的功率"。修改额定制冷量不改变模型输入分布，但必须改变输出量级，否则选型表与实际计算再次脱钩（正是本次要消除的问题）。

**替代方案**：
- 保持内嵌值、选型参数标注为"仅展示"：否决——违反 `equipment-config` 的"单一口径"要求，且报告仍会印出不生效的参数。
- 按新额定值重训模型：否决——超出本 change 范围，且需要新的训练数据。

**局限**：线性缩放假设等效工况下 COP 不变。离心机在相近工况区间内该假设可接受，但会掩盖效率差异。缓解手段见 D6——结果中同时输出"选型标称 COP"与"模型计算 COP"的偏差，使该假设可被观察。

**扩展（任务 0.2 之后补充）：水泵与冷却塔不能沿用线性缩放，必须做相似换算**

线性缩放对冷机成立，是因为它的输入是负荷率与温度（无量纲/强度量）。水泵与冷却塔的输入含**有量纲的流量与风量**，模型见过的数值区间被焊死在 7.4 MW 参考机组上，且代码中存在硬下限：`G_min = Gr × ratio_Hz_min = 182.46 × 0.6 = 109.48 L/s`、`Ga_min = Ga_r × 0.4 = 23,564 m³/h`。

实测后果（把设备直接 ÷26.58 而不做换算）：水泵设计流量 3.80 L/s 被强制拉到 109.48 L/s（超流 28.8 倍），冷却塔风量被拉到 23,564 m³/h，全年能耗由 1,069,854 kWh 暴涨到 **67,504,888 kWh**，系统能效降到 0.0022。

**决策**：按相似（亲和）定律做尺度映射——把实际工作点折算到参考尺度喂给模型，再把输出折算回实际尺度：

```
水泵：G_equiv = G_actual × (Gr_ref / Gr_actual)
      H_equiv = H_actual × (Hr_ref / Hr_actual)
      P_actual = P_model × (Gr_actual / Gr_ref) × (Hr_actual / Hr_ref)
      Gmax/Hmin/Hmax 同 G、H 的比例折算回实际尺度

冷却塔：Gw_equiv = Gw_actual × (Gw_ref / Gw_actual_design)
        Ga_equiv = Ga_actual × (Ga_ref / Ga_actual_design)
        P_actual = P_model × (Ga_actual_design / Ga_ref)
        出水温度 tr_cw 直接透传（温度是强度量，不随尺度变化）
```

**理由**：这样模型始终停留在训练域内，物理上等价于"用同一族几何相似设备的性能曲线"。这也是平台能够比较**不同容量选型方案**的前提——否则它只能仿真一台 7.4 MW 的冷站，而"优化设计方案"正是本项目的立项目标。

**替代方案**：把模型内部参考额定值直接改为实际值。否决理由：权重未变，喂进去的 3.8 L/s 仍在训练域外，等价于外推，结果不可信。

### D6 超装机不再钳制制冷量，缺口显式输出

**决策**：每小时计算 `Q_served = min(Q_demand, Q_installed_active)`，`Q_unmet = Q_demand - Q_served`。冷机负荷率仍钳制到上限参与功率计算（避免模型外推），但制冷量按 `Q_served` 计，缺口逐时累计为结果字段。

**理由**：现状把负荷率钳制到 1.0 却仍以`装机 × 负荷率`作为制冷量，而负荷率已被钳制，导致制冷量小于冷负荷却无任何提示——报告会出现"供冷量 < 冷负荷"而无法解释。

**替代方案**：允许负荷率超过 1.0 由模型外推。否决理由：模型未在超额定工况训练，外推结果不可信，且会污染 COP 统计。

### D7 十二个未生效参数按"生效 / 仅展示 / 移除"三态裁决

**决策**：

| 参数 | 裁决 | 映射方式 |
|---|---|---|
| `n_pump_chw_BCH`、`n_pump_chw_SCH`、`n_pump_cw_BCH`、`n_pump_cw_SCH` | **生效** | 冷冻泵/冷却泵功率 = 单机功率 × 对应泵台数（替换原先统一乘冷机台数） |
| `n_tower_BCH`、`n_tower_SCH` | **生效** | 冷却塔功率 = 单塔功率 × 对应塔台数 |
| `COP_chiller_BCH`、`COP_chiller_SCH` | **仅展示** | 用于"标称 COP vs 模型 COP"的偏差校核，出现在结果中，不参与能耗计算 |
| `Pr_tower_BCH`、`Pr_tower_SCH` | **仅展示** | 选型对照值；塔功率由模型给出 |
| `coe`、`coe_tower_efficience` | **移除** | 无校准语义定义、无法验证，随表单与模型字段一并删除 |

**理由**：台数是典型的"用户以为生效"的参数，报告会印出台数配置，必须真生效；COP 与塔设计功率确实不该覆盖模型输出，但直接删除会让选型表失去可比性，因此降级为"仅展示"并赋予校核用途；`coe` 系列是校准旋钮，在定义出校准流程之前保留即为伪装。

**替代方案**：全部移除。否决理由：台数承载真实选型意图，移除会让报告失真。

**已知局限**：泵/塔与冷机的对应关系仍按"一一对应、台数作乘数与校验"处理。若后续需要"两机一泵"等非对称配置，需扩展管路特性计算——本期不做。

### D8 量纲以"显式声明 + 默认恒等"处理

**决策**：删除 `load_coe` 的三处重复默认值（`1/26.6`、`1/26.58`、前端 `0.0376`），改为单一的量纲换算配置项，默认值为 **`1/1000`（W → kW）**，并在结果 `meta` 中记录换算系数与口径版本。

**依据（任务 0.2 实测，详见 `docs/data-contract.md`）**：以「峰值 ÷ 空调面积」为判据，

| 量 | 原始值 | 按 W 解释 | 按 kW 解释 |
|---|---|---|---|
| 逐时峰值 | 303,067.16 | 303.07 kW → **103.40 W/m²** ✅ | 103,401 W/m² ❌ |
| 年累计 | 149,646,120 | 149,646 kWh → **51.06 kWh/m²·yr** ✅ | 51,056 kWh/m²·yr ❌ |
| 设计负荷 | 196,572.0 | 196.57 kW → **67.07 W/m²** ✅ | 67,067 W/m² ❌ |

结论：数据列与设计负荷的单位都是 W，文件表头声明的 kW 有误。

**原 `1/26.58` 的真实作用**：它不是量纲换算，而是把超配 37.61 倍的装机"缩"到设计负荷的 1.415 倍——`7,394.1 / 196.572 = 37.61`，`37.61 / 26.58 = 1.415`。这是一把为迁就超大装机而设的梯子，它把全部能耗结果放大了 26.58 倍。

**连带改动**：默认值改为 `1/1000` 后，装机必须同步重标定（÷26.58，见 D7 与 `docs/data-contract.md`），且水泵/冷却塔必须做相似换算（见 D5 扩展）。三者缺一不可：

- 只改 `load_coe` 不改装机 → 峰值 303.07 kW 低于启动阈值 316.89 kW，冷站全年不启动
- 只改 `load_coe` 与装机、不做相似换算 → 泵塔硬下限触发，能耗暴涨 63 倍（实测）

**替代方案**：
- 保留 `1/26.58`：否决——它使 EUI = 365 kWh/m²·yr、供冷量 5,527,473 kWh 对一栋 2,931 m² 的办公楼在物理上不成立，而验收场景是出报告
- 默认恒等（1.0）：否决——数据是 W，恒等会让冷站永不启动

**影响提示**：该决策决定后续所有结果的量级。量纲判定（任务 0.2）与配置改造（任务 6.4）保持两个时点：判定先行、改造在后，避免改造做完才发现量纲选错。

**影响提示**：该决策会显著改变结果数值，且决定后续所有结果的量级。因此量纲必须以一个独立的、可核算的步骤先行定死（任务 0.2），确认后再落地本决策的配置改造（任务 6.4）——把判定与改造拆成两个时点，避免改造做完才发现量纲选错、全部结果返工。

**口径版本**：本决策启用口径版本 `v1`，`meta` 记录 `口径版本 = v1`、`量纲换算系数 = 0.001`；跨版本结果不可直接对比。

### D9 前端类型单一来源

**决策**：以 `src/main/src/api/simulation.ts` 的类型定义为唯一来源，删除 `src/main/src/types/index.ts` 中语义漂移的 `WeeklyData`（含不存在的 `totalHeatingLoad`、`progressPercentage`）。

**理由**：两套定义已实际导致雷达图读取不存在的 `coolingLoad` 字段并恒为 0。

**替代方案**：由 OpenAPI 生成类型。否决理由：引入工具链与本 change 目标无关，留待二期。

### D10 碳排放因子以国标公告为准，落配置文件并按年度版本化

**决策**：碳排放量按 `冷源站总耗电量 × 电力二氧化碳排放因子` 计算。因子不再硬编码（现为 `0.5`），而是落在配置文件中，按"发布年度 × 地理口径"组织，每个条目携带来源引用；结果 `meta` 记录实际使用的因子值、地理层级、核算年度与来源公告。地理口径按 `省级 → 区域 → 全国` 逐级回退，实际命中的层级一并记入 `meta`。

**理由**：现有 `0.5` 既无出处也不随年份更新，报告一旦印出碳排放量必然被追问依据。而本项目建筑位于北京，按省级口径应取**北京 0.5554（2023 年）**，与 0.5 相差 **11.1%**；若用全国口径为 0.5306，相差 6.1%；若用华北区域口径为 0.6361，相差 27.2%。三者都合理但结果不同，因此必须显式选择并把选择写进结果。

- 保留单一常量：否决——无法体现年度与地域差异，且违反 `simulation-result` 中"碳排口径至少包含因子取值及来源说明"的要求。
- 请求参数里由用户直接填因子：否决——失去可追溯性，不同用户填不同值就无法横向比较；配置 + 覆盖仅在确有特殊核算要求时开放。
- 改用《关于发布2024年电力碳足迹因子数据的公告》：否决——该公告发布的是**全生命周期碳足迹**因子，用于产品碳足迹核算；本项目核算的是建筑运行的**范围二（外购电力间接）排放**，应使用二氧化碳排放因子而非碳足迹因子。

**回退顺序的取舍**：回退**优先保证年度一致**（同年度内由省级降为区域、再降为全国），而不是跨年度去找同一省份的旧值。理由：能效与碳排的年度对比远不如年度内口径一致重要，混用年度会让碳排放量的时间序列失真。

**已知局限**：公告按年更新，配置需人工同步；跨年度结果对比时因子不一致会被误读为能效变化，故 `meta` 必须记录年度，报告须注明。2023 与 2022 两期公告的省级因子已全部入档（见上表），回退链仅在未来年度尚未发布时才会启用；启用时须在 `meta` 中标记回退层级，使报告可据以说明口径降级的幅度。

### D11 模型适用范围本期由用户配置，训练域留作二期

**决策**：新增"模型适用范围"参数组（室外干球温度上下限、含湿量上下限），由用户在选型表单配置，默认值取设计工况邻域的保守区间。结果 `meta` 声明本次使用的范围，并按该范围输出外推记录数、占比与外推耗电量。

**理由**：设备模型以 `.pth` 权重形式提供，仓库中没有任何训练数据或训练域记录（`model_files/*` 仅含权重与超参文本），因此"真实适用范围"在当前代码里无从获得。硬编码一对上下限等于把决策埋进代码，且无法解释其来源。改为用户配置后，范围成为可声明、可追溯的输入参数，与 `equipment-config` 的"参数生效或标注不生效"原则一致。

**替代方案**：
- 以设计点（干球 31.7 ℃ / 含湿量 0.02347）直接作为上限：否决——设计点是选型工况而非训练域上界，会把大量正常工况误判为外推，导致报告满屏警示。
- 从训练数据统计得出：否决——训练数据未入库，本期无法执行；这正是二期的目标。

**已知局限（须在报告中体现）**：
1. 范围由用户填写，不是模型真实训练域，因此"外推记录数 = 0"只能说明"落在用户声明的范围内"，不等于"模型可信"。
2. 判定使用的是**室外工况**（干球、含湿量），而设备模型的实际输入是负荷率与冷机进出水温。室外工况只是代理指标，真正的模型外推可能发生在水温维度而未被检出。二期引入训练域时，应改为对模型输入维度判定。

**二期方向**：把训练域统计固化为随 `.pth` 一同版本化的模型元数据，用户配置降级为"覆盖项"。

## Risks / Trade-offs

- [模型工况外推] 输入数据干球温度实测最高 37.2 ℃，而设计点 31.7 ℃，模型在训练域外可能失真 → 缓解：按用户声明范围（D11）统计外推记录数、占比与外推耗电量并输出，使失真范围可被观察而非默认忽略；报告须注明该范围非模型真实训练域。
- [线性额定缩放不精确] 见 D5 → 缓解：输出标称 COP 与模型 COP 的偏差，把假设暴露到报告中。
- [口径变更导致历史结果不可比] 移除魔法系数后数值量级会变 → 缓解：`meta` 记录口径版本与换算系数；不做跨版本对比。
- [BREAKING 前端连锁] 多处前端读取旧的周数据结构 → 缓解：任务中逐项列出受影响消费点，提交前用内置 CSV 跑一次端到端核对。
- [全局单例与事件循环阻塞] 本次不解决 → 记录为已知风险：结果按任务字典隔离可降低串扰，但同一时刻的并发仿真的统计量仍可能互相污染；事件循环阻塞会让进度推送出现停顿。二者留待后续 change。
- [泵/塔台数与管路特性解耦不彻底] 见 D7 已知局限 → 缓解：在 `equipment-config` 中要求台数一致性校验，阻止物理上不可能的配置。
- [因子年度不一致被误读] 不同核算年度使用不同因子，跨年对比会把因子变化误读为能效变化 → 缓解：`meta` 记录核算年度与地理层级，报告须注明；禁止跨年度直接对比能效结论。
- [适用范围非真实训练域] 见 D11 已知局限 → 缓解：报告标注"范围由用户声明"，且外推判定仅覆盖室外工况维度，不宣称等于模型可信边界。

## Migration Plan

无数据库、无外部存储，迁移即代码替换，前后端同批发布。

1. **算法层**：设备模型额定值注入（D5）；`station`/`channel` 输出补充供冷缺口与逐时上下文（D3、D6）。
2. **服务层**：`algorithm_wrapper` 实现时间戳贯通、全年覆盖、分项累加、月度聚合、运行统计（D1–D4）。
3. **后端契约与配置**：`schemas.py` 结果模型扩展；参数模型按 D7 裁决增删；新增碳排放因子配置文件（按年度与地理口径组织，D10）与模型适用范围参数组（D11）。
4. **前端同步**：类型单一来源（D9）；修正依赖不存在字段的指标计算；表单按 D7 调整。
5. **验收核对**（可外部复核的三条）：总小时数 = 输入行数；四分项之和 = 总耗电量；供冷缺口 > 0 时必须能定位到具体小时。
6. **回滚**：纯代码回滚，无数据迁移。

## Open Questions

- **输入数据列的真实量纲**：数据文件表头声明为「冷负荷(kW)」，但峰值 303,067 与该建筑面积对应的合理冷负荷相差约三个数量级；现有魔法系数 `1/26.58` 恰好把它换算到与装机容量（7,394 kW）匹配的量级。这是"表头声明错"还是"数值需要换算"，无法从代码推断。**处理方式**：D8 已把换算改为显式配置，因此该问题不阻塞设计。判定动作已固化为任务 0.2（以"峰值 / 空调面积"是否落在同类建筑合理区间为判据），且必须在第 1 组之前完成，结论回写到 D8 的默认值说明。
- **周聚合是否需要在报告中呈现首尾不满周**：报告章节设计属下一 change，不影响本 change 的数据契约（首尾不满周带实际小时数即可）。
- **因子配置的存放位置**：因子表属运行时配置还是随代码版本化的常量数据，取决于后续是否要求「更换因子无需重启」。本 change 按「版本化配置文件、重启生效」处理；若需热更新则改为读取外部存储，属可迭代项，不影响本 change 的契约。
