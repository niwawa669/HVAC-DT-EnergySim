# Design

## Context

动机与行为契约见 `proposal.md` 与本次三份 delta spec。本文只记录实现取舍。

**当前状态**

- 冷机 COP（`COP_chiller_BCH/SCH`）、冷冻泵与冷却泵设计流量、冷却塔设计水流量**全部是手工输入**，且 COP 与塔功率被标为"仅展示"
- 手工值之间存在物理矛盾：大机冷却塔水流量 4,000 L/s，而冷却泵只有 2,522 L/s（1.6 倍）
- 报告的参数快照已改为实际值，但"实际值"取自提交的配置，而配置这些字段本身就是手填的

**已确认的两处决策**

- 冷却塔设计功率：按设计点归一参与计算（问题一 A）
- 派生字段：从请求中移除，后端唯一计算（问题二 A）

## Goals / Non-Goals

**Goals**

- 设计页只保留**独立输入**；凡是能从额定容量与设计工况推出的量，都不允许手工填写
- 报告与设计页对应字段逐项相等，来源唯一

**Non-Goals**

- 不改设备模型的训练与权重
- 不改冷机台数、群控策略的既有逻辑
- 不引入新的设备类型

## Decisions

### D1 派生关系与计算式

设单机实际容量 Q（= 基准容量 × 放大系数）、冷冻水温差 ΔT_chw、冷却水温差 ΔT_cw：

| 派生量 | 计算式 |
|---|---|
| 冷机 COP | `Q ÷ P_model(load=1.0, tr_chw, ts_chw, tr_cw, ts_cw)` |
| 冷冻泵设计流量 | `Q ÷ (4.187 × ΔT_chw)` |
| 冷却泵设计流量 | `Q × (1 + 1/COP) ÷ (4.187 × ΔT_cw)` |
| 冷却塔设计水流量 | 等于冷却泵设计流量 |

其中 4.187 kJ/(kg·℃) 为水的比热容，水的密度取 1 kg/L。冷却侧采用冷凝负荷 = 制冷量 + 冷机功率，故出现 `1 + 1/COP`。

以默认配置（放大系数 20，7 大机 + 1 小机）为例，两种机型 COP 相同（同一模型、同一设计温度）：

| 项 | 大机 | 小机 |
|---|---|---|
| 额定制冷量 | 42,252 kW | 21,126 kW |
| 模型 COP | 6.8235 | 6.8235 |
| 冷冻泵流量 | 2,018.25 L/s | 1,009.12 L/s |
| 冷却泵流量 | 2,314.03 L/s | 1,157.01 L/s |
| 冷却塔水流量 | 2,314.03 L/s | 1,157.01 L/s |

**替代方案**：把这些量保留为可编辑但带"默认推导值"的输入。否决理由：用户一旦改成不一致的组合，报告与物理就同时失去约束，这正是本次要消除的问题。

### D2 派生字段从请求中移除

`COP_chiller_BCH/SCH`、`Gr_pump_chw_*`、`Gr_pump_cw_*`、`Gr_tower_*` 不再出现在请求模型中；它们由后端在仿真开始时计算并写入 `meta.parameters`。前端用同一套公式展示，但**后端是唯一事实源**。

**理由**：两处计算公式并存必然漂移。移除后，"请求里传了什么、实际用了什么"不再可能不一致。

**代价**：这是破坏性接口变更，前端与后端必须同批发布；且这些字段在结果快照中由"回显提交值"变为"派生值"。

**替代方案**：保留字段、后端覆盖。否决理由：会留下"传了也没用"的僵尸字段，与「参数生效原则」冲突。

### D3 冷却塔设计功率：按设计点归一

`k_tower = 设计功率 ÷ P_model(设计工况)`；实际风机功率 = `P_model(当前工况) × k_tower`。

**理由**：设计工况下恰好等于用户输入的设计功率（选型意图被尊重），偏离设计工况时仍保留模型给出的相对变化（部分负荷特性不被抹平）。

**替代方案**：风机功率恒等于设计功率。否决理由：塔风机是变工况运行的，恒功率会让全年塔耗电量与负荷无关。
**替代方案**：只作标称校核。否决理由：那就必须保留"仅展示"，与本次需求冲突。

### D6 每台设备按自身模型参考点归一（实施中发现，修订 D1 的尺度定义）

**决策**：冷机用 `Q / 2112.6`、冷冻泵用 `G_chw / 182.46`、冷却泵用 `G_cw / 182.46`、冷却塔用 `Gw / 200`。

**为什么改**：原方案令三台设备共用冷机尺度（20）。冷却塔按新规则的水流量是 2,314 L/s，除以 20 得 115.7 L/s，仅为塔模型参考点 200 L/s 的 58%，模型被迫外推，输出随负荷**非单调**（20%/40% 负荷算出 1,882/2,078 kW，60% 负荷只有 47 kW），全年塔耗电量出现**负值**。

改用塔自身参考点后，模型在设计工况收到精确的 (200 L/s, 58,910 m³/h)，出水温度 33.17 ℃、设计点功率 440 kW，行为正常；冷冻泵同理收到 182.46 L/s。塔耗电量转正，且设计功率翻倍时耗电量精确翻倍（比例 2.000000）。

**替代方案**：只修冷却塔、泵维持冷机尺度。否决理由：泵同样会偏离参考点（100.9 vs 182.46），只是后果没塔那么显眼；统一按各自参考点更简单也更可解释。

### D4 请求中不再有"仅展示"参数

`meta.displayOnly` 与 `displayOnlyDeviations` 对新结果将为空数组/空对象。保留这两个字段是为了兼容历史结果（v1/v2 的报告仍需按标注渲染），不删除。

### D5 加机优先级的呈现

报告把 `Qr_list` 渲染为「小机 21,126 kW → 大机 42,252 kW」，而不是 `[21126.0, 42252.0]`。序列仍以 [小机, 大机] 为序，与 `n_design_list` 一致。

## Risks / Trade-offs

- [破坏性接口变更] 移除 7 个请求字段 → 前后端同批发布；旧客户端会收到 422 并看到明确原因。
- [COP 随设计温度变化] COP 现在由设计工况决定，用户改设计温度会连带改变 COP 与两个泵流量 → 界面需给出联动提示，避免用户以为改了没用。
- [塔功率归一系数的数值稳定] 若设计工况下模型功率极小或异常，`k_tower` 会被放大 → 对 `P_model` 加下限保护，并在结果中记录 `k_tower`。
- [报告与设计页"相等"的可验证性] 两处若用不同精度或不同舍入会看起来不等 → 统一由后端派生、前端展示同一份数值，报告直接取快照。

## Migration Plan

1. 后端：派生计算 + 请求字段移除 + 快照写入
2. 算法层：塔功率归一系数接入 `Tower`
3. 前端：五个字段改只读派生、去掉"仅展示"、联动提示
4. 报告：加机优先级可读化、参数表取快照
5. 回归：默认配置下报告第 3 章与设计页逐项对比
